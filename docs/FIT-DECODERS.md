# Swapping fitparse for a faster FIT decoder: the evidence

Measured 2026-10-19/20 for the TODO entry **Decide whether to swap fitparse for a faster FIT decoder**.

- **Evidence.** Headwind's real `parse_fit`, unchanged, over all 2,315 FIT files of the test export (`~/headwind-local/strava-export.zip`, 403 MB), with each decoder underneath behind a stand-in `fitparse` module; every output field compared with fitparse's. Scripts, timings and the full reports are in `~/headwind-local/fit-decoder-bench/` (README.md says how to run it again). fitparse 1.2.0, fitdecode 0.11.0, garmin-fit-sdk 21.218.0, Python 3.13. The field comparison ran before `_map_sport` took the session's `sub_sport` (the sport fix under Bugs); the sport is checked separately below.
  - **Time**, the whole of `parse_fit`: fitparse 657 s (median 0.138 s a file), fitdecode 434 s (0.094 s, −34%), garmin-fit-sdk 314 s (0.067 s, −52%). That's about 4 or 6 minutes off a full import of the export (about 16 minutes today), less than the decoders alone suggest (13.3 / 6.1 / 3.8 s on 40 files), because `parse_fit`'s own work stays. No errors with any of them; two fitparse runs gave identical output.
  - **Activity ids.** Both return UTC-aware datetimes, and `_stable_id` hashes `start.isoformat()`, so swapped in as they are, every FIT activity gets a new id ('+00:00' in the key) and would come in again beside itself. With the times made naive UTC, every id matches.
  - **fitdecode**: 2,186 of 2,315 files identical. The other 129 only gain a lap `strokes` on rides (it resolves `total_cycles` to the `total_strokes` subfield); the activity page only reads strokes for pool lengths. No stream or summary differences.
  - **garmin-fit-sdk**: 1,370 identical, and it never contradicts fitparse (no lap value differs); it fills in what fitparse misses:
    - lap `mps` (1,591 laps), `cad` (1,298) and `strokes` (1,671);
    - `averageCadence` on 225 runs and `maxCadence` on 50 (fitparse renames `avg_cadence` to `avg_running_cadence`, so `parse_fit` misses it);
    - the device's `enhanced_avg_speed` / `enhanced_max_speed` on newer Garmin watches (product 3290): `averageSpeed` changes on 370 files, all but 5 by under 1% (most are the device's 3 decimals against Headwind's distance / moving time); `maxSpeed` on 163;
    - the record distance in Zwift files: 206 distance streams differ, all 206 ending within 0.5% of the session distance, against 190 of 206 with fitparse (the stream from the track runs short, e.g. 44,652 m against 44,818 m);
    - barometric altitude and speed on 3 ski days, where fitparse reads them on only some records.
  - **garmin-fit-sdk's defaults.** `merge_heart_rates` (on by default) overwrites record HR from the file's `hr` messages: e-MTB ride 16246829413 averaged 143.9 against the session's 145; with it off, HR matches fitparse. Invalid floats come back as NaN where fitparse gives None.
  - **What the extra device figures would change.** A walk (13746796500) would take the device's `maxSpeed` of 7.13 m/s (26 km/h), a GPS spike, against 1.42 on its track, because `parse_fit` takes any device maximum up to 30 m/s (`_MAX_PLAUSIBLE`) whatever the sport. 4 other maxima rise over 25%, all plausible (walks and slow rides at 3 to 3.6 m/s). 4 pool swims' `averageSpeed` would leave out the rests (e.g. 0.81 to 0.98 m/s). One ski day's (14766841875) device average is over timer time, not moving time (3.11 to 2.75 m/s).
  - **Sport and sub-sport.** Since the sport fix, `parse_fit`'s sport comes from the session's `sport` and `sub_sport` names (`_map_sport` → `sports.from_type`), and those names come from each decoder's copy of Garmin's FIT profile: fitparse's is SDK 20.8 (March 2019), fitdecode's 21.171 (2025), garmin-fit-sdk's 21.218. A value a decoder's profile doesn't know comes back as a bare number. fitparse lacks 32 sports and 51 sub-sports that garmin-fit-sdk has, fitdecode 13 and 23; where both know a value they name it the same.
    - On the test export, no file's sport changes: mapped through the working tree's `_map_sport`, all three give the same sport for all 2,315 files. fitparse returns numbers on 93 of them, 91 `hiit` sessions (sport 62) and 2 padel games (sport 64 `racket`, sub-sport 85 `padel`), but those come out as Other either way.
    - Values the test export doesn't have would change: with fitparse, sports `wheelchair_push_walk` (Walk), `wheelchair_push_run` (Run), `disc_golf` (Golf), `wakesurfing` (Surf) and `canoeing` (Paddle), and cycling + `e_bike_enduro` (EBikeRide), all come in as Other (or Ride for the e-bike) because they arrive as numbers. fitdecode misses only `canoeing` and `e_bike_enduro`; garmin-fit-sdk knows them all. This hits uploaded FIT files today, whichever decoder is chosen later (a Garmin sync takes the sport from Garmin's activity type, `garmin.garmin_sport`); keeping fitparse means it stays.
    - A switch can also change the sport of a file already imported, since the next import reads every file again (`READER_LIBRARIES`): none do on the test export, but the re-run should compare `sportType` too. The scan is `sports_of.py` / `sports_cmp.py` and the profile comparison `enums.py` in `~/headwind-local/fit-decoder-bench/`.
